# Cedar conformance corpus

This directory drives nxe-cedar's **behavioral conformance** check against the
official Rust Cedar implementation, using the auto-generated differential-test
corpus published by the Cedar team. It gives the project a concrete, repeatable
metric — "C-vs-reference parity on the official corpus" — to stand in for the
formal-verification gap (Cedar's Lean proofs do not extend to a C
reimplementation, and the Cedar team discourages Lean→C codegen; running the
official corpus in CI is the same approach StrongDM uses for its Go port).

  (corpus generated with Cedar `4.1.0`).
- Oracle: the `cedar-policy` crate (currently `4.9.1`) linked by `tests/ffi`.

Refresh the pin manually when bumping to a new Cedar major version: update the
SHA in `Taskfile.yml` and here, delete `.cache/`, and re-run.

## How it runs

The runner is `tests/ffi/tests/conformance_test.rs`, gated behind the
`conformance` Cargo feature so the default `cargo test` is unaffected and no
extra crates are pulled in. It reads an **already-unpacked** corpus directory
(`CEDAR_CORPUS_DIR`, default `tests/conformance/.cache`) with `std::fs` only —
fetching and unpacking the tarball is the Taskfile's job, which keeps HTTP and
archive crates out of the build.

```bash
# fetch (once) + run
task test type=conformance

# offline: place corpus-tests.tar.gz under tests/conformance/.cache/ and unpack,
# or point at any directory containing `corpus-tests/`:
CEDAR_CORPUS_DIR=/path/to/extracted cargo test -p cedar-ffi-test \
  --features conformance --test conformance_test -- --nocapture --test-threads=1
```

Useful env knobs: `CEDAR_CORPUS_LIMIT=N` (only the first N test files),
`CEDAR_CORPUS_FAIL_DETAIL=N` (capture N failures with full detail),
`CEDAR_CONFORMANCE_MIN_RATE=NN.N` (override the parity floor).

## What is checked (two tiers)

Each corpus request is evaluated in two stages:

1. **Oracle fidelity** — the live `cedar-policy` crate, over the *full*
   cedarJson entity store, must reproduce the corpus's published `decision`.
   A mismatch (i.e. the linked Cedar disagrees with the corpus-generation
   Cedar) is recorded as `version_skew` and excluded from the C comparison.
2. **C parity** — the corpus entities are translated into the flat request JSON
   that the existing C wrapper / FFI oracle already consume (attributes and the
   transitive ancestor closure of principal/action/resource only). The C
   decision must equal the oracle. If flattening would change the decision the
   case is skipped as `translation_lossy`; known-unsupported syntax is skipped
   by category (below).

Every divergence outside nxe-cedar's documented subset is reclassified as a
counted skip, so the in-subset corpus is expected to reach 100%. The test
asserts the C-parity rate stays at or above a floor (default 100.0%) and prints
every unclassified divergence — any such mismatch must be fixed or explicitly
classified.

## Skip categories

Skips are counted, not failed — they record where the corpus exercises syntax
or a model that is outside nxe-cedar's documented subset:

| Category | Meaning |
| --- | --- |
| `nul_byte` | Attribute key/value/string contains a NUL byte (fuzzer artifact); cannot cross the C-string / jansson boundary. Harness limit, not a semantic difference. |
| `entity_tags` | Policy uses `.hasTag` / `.getTag` — entity tags are not implemented (see `docs/FEATURES.md`). |
| `block_comment` | Policy uses `/* … */`; nxe-cedar accepts `//` only. |
| `parse:*` | nxe-cedar's parser is intentionally stricter than the reference: it rejects empty attribute keys (`parse:empty_bracket_key`, `parse:bad_record_key`), non-literal extension constructor arguments (`parse:nonliteral_extn_arg`), more than 16 annotations (`parse:too_many_annotations`), and other fuzzer-malformed constructs the reference parses permissively (`parse:expected_*`, `parse:other`). |
| `known_gap:entity_literal_access` | Attribute / `has` access directly on an entity *literal* (e.g. `Foo::"id".bar`). Access on a literal denoting a **request** entity is resolved via its slot (issue #042) and stays in the compared set; only literals denoting **non-request** entities are classified here — they need a general entity store (out of scope; tracked with #033). A literal matching a request entity is never reclassified, so a regression in that path still fails. |
| `known_gap:derived_entity_attr` | Dereference (`.attr` / `has` / `in`) of an entity-valued *attribute* (e.g. `(a::"x".o).o`, `(resource.r).r in …`). The intermediate value is a *derived* entity (an attribute-lookup result), which is not slot-backed, so nxe-cedar cannot resolve its attributes/ancestors. General entity-store boundary (out of scope; tracked with #033). |
| `version_skew` | Linked Cedar disagrees with the corpus-published decision. |
| `translation_lossy` | Flattening the entity store to the C envelope would change the decision. |
